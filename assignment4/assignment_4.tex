        \item (5 pts) Write a function \verb|totalDistance(D, path)| which returns the total distance a traveling salesman must travel given a sequence of cities. \verb|path| will include each city exactly once, note that the salesman must end at the start city. Submit your code on INGInious and include a code snippet of this function in your PDF submission.

\paragraph{Answer.}
I add each distance along the route. Then I include the trip back home. That last edge matters. An empty route returns zero.

\begin{lstlisting}
def totalDistance(D, path):
  if not path:
    return 0.0
  return float(sum(D[path[j]][path[(j + 1) % len(path)]]
          for j in range(len(path))))
\end{lstlisting}

I visit each listed edge once. That takes $O(n)$ time and $O(1)$ extra space.

        \item (10 pts) Write a function \verb|nearestNeighbor(D, start)| which returns an order in which to visit cities with associated distance matrix \verb|D| starting at \verb|start| and following the nearest neighbor heuristic. Submit your code on INGInious and include a code snippet of this function in your PDF submission. What is the asymptotic runtime of this function?

\paragraph{Answer.}
I start at the given city. A start of -1 picks one randomly. Then I choose the nearest unvisited city. Ties go to the smaller city index.

\begin{lstlisting}
def nearestNeighbor(D, start=-1):
  n = len(D)
  if n == 0:
    return []
  if start == -1:
    start = int(np.random.randint(n))
  path = [start]
  remaining = set(range(n))
  remaining.remove(start)
  while remaining:
    city = min(remaining, key=lambda v: (D[path[-1]][v], v))
    path.append(city)
    remaining.remove(city)
  return path
\end{lstlisting}

I check $n-1$ cities, then $n-2$, and so on. These checks add up to $n(n-1)/2$. So the runtime is $\Theta(n^2)$. Matrix access and expected set operations take constant time. I also use $O(n)$ extra space. The greedy choices can miss a better tour.

        \item (5 pts) Write three functions to generate candidate solutions.
        \begin{itemize}
            \item \verb|swapPairs(path, numSwaps, adj)| swaps \verb|numSwaps| random pairs of elements in \verb|path|. If \verb|adj| is \verb|True|, only swap adjacent pairs of elements in the current path.
            \item \verb|permuteRange(path)| randomly permutes a slice of \verb|path| between two randomly selected indices.
            \item \verb|reverseRange(path)| reverses a slice of \verb|path| between two randomly selected indices.
        \end{itemize}
        Include code snippets of these functions in your PDF submission.

\paragraph{Answer.}
I copy the path before changing it. That leaves the input alone. Adjacent swaps use consecutive list positions, without wrapping around. For slices, I include both randomly selected endpoints. Paths shorter than two cities stay unchanged.

\begin{lstlisting}
def swapPairs(path, numSwaps=1, adj=False):
  candidate = path[:] #we do not want to change the given path
  n = len(candidate)
  if n < 2:
    return candidate
  for _ in range(numSwaps):
    if adj:
      a = int(np.random.randint(n - 1))
      b = a + 1
    else:
      a, b = np.random.choice(n, size=2, replace=False)
    candidate[a], candidate[b] = candidate[b], candidate[a]
  return candidate
\end{lstlisting}

\begin{lstlisting}
def permuteRange(path):
  candidate = path[:] #we do not want to change the given path
  if len(candidate) < 2:
    return candidate
  a, b = sorted(np.random.choice(len(candidate), size=2, replace=False))
  candidate[a:b + 1] = np.random.permutation(candidate[a:b + 1]).tolist()
  return candidate
\end{lstlisting}

\begin{lstlisting}
def reverseRange(path):
  candidate = path[:] #we do not want to change the given path
  if len(candidate) < 2:
    return candidate
  a, b = sorted(np.random.choice(len(candidate), size=2, replace=False))
  candidate[a:b + 1] = candidate[a:b + 1][::-1]
  return candidate
\end{lstlisting}

Shuffling can leave a slice unchanged. Several swaps can also undo earlier swaps. Both still produce valid candidates.

With fixed swaps, each function takes $O(n)$ time. Copying the route already takes that long. NumPy's sampling may build a full permutation. For $s$ swaps, a conservative bound is $O(n(1+s))$. Extra space is $O(n)$.

        \item (10 pts) Write a function \verb|runSimulatedAnnealing(D, genCandidate, maxIterations, T, alpha)| which finds a path for a traveling salesman using simulated annealing given a distance matrix \verb|D|, a function to generate candidate solutions, a maximum number of iterations to perform, an initial temperature, and a multiplicative update factor for temperature. The initial path should be a random permutation of the cities. Include a code snippet of this function in your PDF submission. What is the asymptotic runtime of this function with respect to $n$ (the number of cities) and $i$ (the number of iterations)?

\paragraph{Answer.}
I begin with a random tour. I always accept equal or shorter candidates. Longer candidates get a chance too. Their acceptance probability is $e^{-\Delta/T}$ when $T>0$. I multiply the temperature by alpha each iteration.

I track the best tour separately. An accepted uphill move cannot erase that record. At zero temperature, I reject uphill moves. The distance list records each iteration's current distance.

\begin{lstlisting}
def runSimulatedAnnealing(D, genCandidate=swapPairs, maxIterations=1000, T=-1, alpha=0.9):
  if T==-1: T = np.sqrt(len(D)) #default starting temperature
  T = float(T)
  curPath = np.random.permutation(len(D)).tolist() #a random initial path
  curDist = totalDistance(D, curPath)
  bestPath, bestDist = curPath[:], curDist
  distList = []
  for _ in range(maxIterations):
    candidate = genCandidate(curPath[:])
    candidateDist = totalDistance(D, candidate)
    delta = candidateDist - curDist
    if delta <= 0 or (T > 0 and np.random.random() < np.exp(-delta / T)):
      curPath, curDist = list(candidate), candidateDist
      if curDist < bestDist:
        bestPath, bestDist = curPath[:], curDist
    distList.append(curDist)
    T *= alpha
  return bestPath, bestDist, distList
\end{lstlisting}

Each provided generator takes $O(n)$ time. Scoring and copying routes also take $O(n)$. For $i$ iterations, the runtime is $O(n+in)$. Extra space is $O(n+i)$, including the history.

Those bounds assume at least one city. Including empty inputs gives $O((i+1)(n+1))$ time. For a general generator taking $G(n)$ time, the runtime becomes $O(n+i(n+G(n)))$.

The current distance sometimes rises early. That comes from accepting uphill moves. Later, the curves mostly decrease in steps. A plateau does not prove optimality.

The default cooling gets cold pretty quickly. After 100 updates, $T$ is about $0.000266$. After 200, it is about $7.06\times10^{-9}$. Most remaining iterations behave like greedy improvement.

I would sample uphill changes before choosing a temperature. I could target an initial acceptance probability of 0.8. A typical uphill change helps estimate that temperature.

I would use $T_0\approx-\Delta_{\mathrm{typical}}/\log(0.8)$. Then I would choose a final temperature. The schedule becomes $\alpha=(T_{\mathrm{final}}/T_0)^{1/i}$. This spreads cooling across the iteration budget.

I would compare several seeds under equal evaluation budgets. I would share matrices and starting tours when comparing methods. Then I would check fresh instances. These single runs cannot establish a consistent winner.

    \item Let us return to the busy beaver numbers.
    \begin{enumerate}
        \item (5 pts) Describe why the busy beaver numbers are incomputable intuitively. What are the practical consequences of this with respect to determining $BB(n)$?

\paragraph{Answer.}
I use the course's step-count definition of $BB(n)$. It measures the longest halting run among $n$-state machines. They use binary tapes, initially filled with zeros. The separate halt state does not count. This matches the earlier $BB(2)=6$ convention.

For fixed n, only finitely many machines exist. Each halting machine has a finite runtime. So the maximum halting time is finite.

The trouble is identifying every machine that never halts. Running one longer does not settle that question. It might still halt much later. A computable time bound would decide halting. That is impossible.

I can find lower bounds using halting examples. Longer searches might improve those bounds. A cutoff cannot generally establish the exact maximum. I need proofs covering the remaining machines. Some small values can be established. No single algorithm can compute every $BB(n)$.

        \item (10 pts) Show that the busy beaver numbers are incomputable via reduction from a problem discussed in class. In particular, write pseudocode (using Python syntax) showing that a known undecidable problem can be solved assuming the existence of a function \verb|BB(n)| which is guaranteed to halt.

\paragraph{Answer.}
I assume $BB(n)$ is computable and always halts. I would use it to decide the halting problem.

I start with a machine M and input w. I construct a blank-start, binary-tape machine N. It first writes an encoding of w. Then it simulates M on that input. This finite construction preserves whether the machine halts.

I count N's working states, including the added setup states. Using only M's original state count would be wrong.

\begin{lstlisting}

def decideHalting(M, w):
    N = compileToBinaryBlankStart(M, w)
    n = numberOfWorkingStates(N)
    limit = BB(n)
    config = blankConfiguration(N)
    if isHalted(config):
        return True
    for _ in range(limit):
        config = step(N, config)
        if isHalted(config):
            return True
    return False


\end{lstlisting}

The initial check covers halting without any transitions. Each later check follows a simulated transition. That includes halting exactly at the bound.

If N halts, its runtime cannot exceed $BB(n)$. If it survives that bound, it cannot halt later. Otherwise it would exceed the maximum. The procedure therefore answers halting correctly.

The assumed BB call terminates. The bounded simulation also terminates. Together they would decide an undecidable problem. So a total computable BB function cannot exist.

This argument uses halting time, not printed-one counts. A bound on printed ones needs a different reduction. It cannot directly bound the number of steps.
